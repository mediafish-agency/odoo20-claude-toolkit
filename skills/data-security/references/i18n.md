# Translations and i18n files (Odoo 20)

How Odoo 20 translates code terms (`self.env._`, `_`, `LazyTranslate`), field values
(`translate=`), views and data records, how the module `i18n/` folder is laid out and how to export,
import and load languages with `odoo-bin i18n`. The rules for *what* to put inside `_()` are Odoo's own:
[Translate only static literals](../../odoo-guidelines/guidelines/python.md#translate-only-static-literals).

## Code terms in Python

| API | Import | Language used |
|---|---|---|
| `self.env._("text %s", arg)` | none (method of `Environment`) | `env.lang` (`en_US` when unset) |
| `_("text %s", arg)` | `from odoo import _` (also `odoo.tools`) | guessed from the caller's frame (`self.env`, `context`, `uid`...) |
| `_lt` / `LazyTranslate` | `from odoo.tools import LazyTranslate` or `odoo.tools.translate` | resolved when converted to `str` or passed to `env._()` |

```python
# addons/sale/models/sale_order.py:1455 and 2491-2495
if vals.get("name", self.env._("New")) == self.env._("New"):
    ...
note=order.env._(
    "Upsell %(order)s for customer %(customer)s",
    order=order_ref,
    customer=customer_ref,
)
```

- Pass values as positional **or** keyword arguments, never both (asserted). Markup arguments make
  the translation escaped; list/tuple arguments are rendered with `format_list` in the target
  language; lazy arguments are translated too.
- A bad translation (placeholders not matching) falls back to the source string and logs the error.
- Python code terms are read from the module's `.po` files on disk and cached per process
  (`CodeTranslations`): after editing a `.po`, restart the server; no DB import is needed for them.
- Extraction recognises the call names `_` and `_lt` (Python) and `_t` (JS): `self.env._(...)` is
  extracted because the called name is `_`; a translation function under any other name is invisible
  to `i18n export`.

## Lazy terms for module constants

```python
# addons/account_peppol/tools/peppol_errors.py:7 pattern; docstring of odoo/tools/translate.py:1157-1166
from odoo.tools import LazyTranslate

_lt = LazyTranslate(__name__)          # bind the module once; keep the name `_lt`
LABEL = _lt("User")

def _compute_label(self):
    env = self.with_context(lang=self.partner_id.lang).env
    self.user_label = env._(LABEL)       # translate in the record's language
```

- `LazyTranslate(module, *, default_lang='')`; in module `base` the default language is `en_US`.
- A `LazyGettext` is not hashable and not orderable (`__hash__`/`__lt__` raise): do not use it as a
  dict key or sort it; `str + lazy` concatenation translates on the spot.
- Never call `_()` at import time (module/class level); see the
  [official note](../../odoo-guidelines/guidelines/python.md#exceptions-and-notes).

Source: odoo/tools/translate.py:1146-1240, odoo/addons/base/models/ir_access.py:12-45

## Translatable field values

| Declaration | Granularity | Typical use |
|---|---|---|
| `fields.Char(translate=True)` / `Text` / `Html` | whole value per language | names, descriptions |
| `fields.Html(translate=html_translate)` | per term (text nodes / translatable attributes) | rich descriptions (`addons/account/models/account_tax.py:117`) |
| `fields.Text(translate=xml_translate)` | per term in XML | view arch (`ir.ui.view.arch_db`) |

```python
from odoo.tools.translate import html_translate   # also exported by odoo.tools

description = fields.Html(string='Description', translate=html_translate)
```

- Stored as a `jsonb` column `{"en_US": ..., "fr_FR": ...}`; reads and writes use `env.lang`
  (`en_US` when unset). Switch language with `record.with_context(lang='fr_FR')`.
- A translated field cannot depend on context (asserted when the cache is filled).
- Several languages at once: `record.update_field_translations('name', {'fr_FR': 'Bonjour', 'nl_NL': False})`
  (`False` removes a translation); for callable `translate` the value is `{lang: {old_term: new_term}}`.
  Read them with `record.get_field_translations('name', langs=['fr_FR'])`.
- Field metadata (`string`, `help`, selection labels) is translated automatically through `ir.model.*`
  records; never wrap them in `_()`.

## Views, QWeb and data records

- View arch and QWeb templates: text nodes are translated, plus these attributes:
  `string`, `add-label`, `help`, `sum`, `avg`, `confirm`, `placeholder`, `alt`, `title`,
  `aria-label`, `aria-keyshortcuts`, `aria-placeholder`, `aria-roledescription`, `aria-valuetext`,
  `value_label`, `data-tooltip`, `label`, `confirm-label`, `cancel-label`, `confirm-title`, and
  their `t-attf-` variants. Any attribute named `*.translate` is translated, e.g. a v20 `t-call`
  parameter `<t t-call="x" c.translate="Some text"/>`.
- Opt out on a node with `t-translation="off"`; `script`, `style`, `title` elements are skipped.
- Data files can carry translations inline: `<field name="name@th">...</field>` in XML
  (`addons/l10n_th/data/account_tax_report_data.xml:5`) or a `name@fr` column in CSV. The loader
  skips these when creating records; they are imported as translations. Tag syntax:
  [data-files.md](data-files.md).
- Mail templates are translated per field (`subject`, `body_html` per term) and rendered in the
  `lang` expression's language: [mail-data.md](mail-data.md).

## The i18n folder

```text
my_module/
  i18n/
    my_module.pot     # template, written by "odoo-bin i18n export my_module"
    fr.po             # base language, file name = res.lang iso_code
    fr_BE.po          # optional variant, loaded after fr.po (overrides it)
    es_419.po         # Latin-American Spanish base for es_AR, es_MX, ...
  i18n_extra/         # optional second folder, same naming, also loaded
```

- Lookup order for language `xx_YY`: `xx.po`, then (Spanish other than `es_ES`/`es_419`) `es_419.po`,
  (`zh_HK`) `zh_TW.po`, then `xx_YY.po`; each in `i18n/` then `i18n_extra/`.
- Entry comments tell where a term comes from: `#. odoo-python` + `#: code:addons/...:0` (Python),
  `#. odoo-javascript`, `#: model:ir.model.fields,field_description:...`,
  `#: model_terms:ir.ui.view,arch_db:...` (per-term fields).
- Do not hand-edit the `.pot`: re-export it. Translators work on `.po` files.

## odoo-bin i18n

All subcommands take `-c/--config FILE` and `-d/--database NAME` (exactly one database) and run
without HTTP. Modules must be installed in that database; languages must be installed for export.

| Subcommand | Arguments |
|---|---|
| `export` | `MODULE...` (positional, required), `-l/--languages LANG...` (default `pot`; `pot` = template), `-o/--output FILE` (`.po`, `.pot`, `.tgz`, `.csv`, or `-` for a `.po` on stdout; one language only; no `.csv` for the template) |
| `import` | `FILE...` (positional, `.po` or `.csv`), `-l/--language LANG` (required), `-w/--overwrite` |
| `loadlang` | `-l/--languages LANG...` |

```bash
# write my_module/i18n/my_module.pot (default) into the module folder
./odoo-bin i18n export -d mydb my_module
# write my_module/i18n/fr.po and de.po; put modules BEFORE -l (it is greedy)
./odoo-bin i18n export -d mydb my_module -l fr_FR de_DE
# one file for several modules
./odoo-bin i18n export -d mydb sale stock -l fr_FR -o /tmp/fr.po
# install languages, then import a file, overwriting existing terms
./odoo-bin i18n loadlang -d mydb -l fr_FR es_AR
./odoo-bin i18n import -d mydb -l fr_FR -w my_module/i18n/fr.po
```

- `-l` matches either `res.lang.iso_code` or `res.lang.code`; unknown or not installed languages are
  skipped with a warning (the warning prints the `loadlang` command to run).
- Server options (not the subcommand): `--load-language=fr_FR,de_DE` installs languages at start-up,
  `--i18n-overwrite` overwrites existing terms during `-u` (rejected without an update option).
- Run it through `odoo_shell` / `odoo_job` on a throwaway DB, or `odoo_test` to check a module
  installs with its `.po` files.

## How translations reach the database

| Kind | Stored | Loaded when |
|---|---|---|
| Python / JS code terms | not in DB; read from `.po` files at runtime | first use per (module, lang), cached per process |
| Field values, view arch, data records, field labels | `jsonb` translated columns | language install (`loadlang`, `--load-language`, settings) and module install/update for installed languages |
| Existing DB terms on update | kept unless `--i18n-overwrite` / `import -w` | |

Testing a translation: `record.with_context(lang='fr_FR').name` after `loadlang`, or
`self.env['res.lang']._activate_lang('fr_FR')` in tests (verify the method with `odoo_method`).

Source: odoo/tools/translate.py:2588-2645, odoo/orm/fields_textual.py:52-60

## Formatting per language

`from odoo.tools import format_date, format_datetime, format_amount, formatLang, format_list, get_lang`

- `format_amount(env, amount, currency, lang_code=None, trailing_zeroes=True)`,
  `format_date(env, value, lang_code=..., date_format=...)`, `get_lang(env, lang_code=None)` returns
  the `res.lang` data (date format, separators).
- In mail templates the same helpers exist as `format_date(...)`, `format_amount(amount, currency)`
  without `env` (see [mail-data.md](mail-data.md#render-engines-inline_template-vs-qweb)).

## v19 habit -> Odoo 20

Translation APIs are unchanged between 19 and 20; these are older habits still seen in custom code.

| v19 / older | Odoo 20 | Source |
|---|---|---|
| `_("...")` in model methods | `self.env._("...")` (official guideline) | odoo/orm/environments.py:344 |
| `from odoo import _lt` / `_lt = LazyGettext` | `_lt = LazyTranslate(__name__)` per module | odoo/tools/translate.py:1216-1240 |
| `ir.translation` records / `_ir_translation` table | `jsonb` columns + `update_field_translations` | odoo/orm/models.py:2821 |
| `odoo-bin --i18n-export=x.po --modules=x` | `odoo-bin i18n export x -l fr_FR -d db` | odoo/cli/i18n.py |
| `odoo-bin --i18n-import=... --language=fr_FR` | `odoo-bin i18n import -l fr_FR FILE` | odoo/cli/i18n.py |
| `t-esc` in translated QWeb | `t-out` (validator XML003) | odoo/addons/base/models/ir_qweb.py |
| `t-set` inside `t-call` to pass a translated label | `<t t-call="x" label.translate="Text"/>` (XML012) | odoo/tools/translate.py:128-133 |
