## ir.cron: the model

`ir.cron` delegates to `ir.actions.server` (`_inherits = {'ir.actions.server': 'ir_actions_server_id'}`),
so a cron record also carries `name`, `model_id`, `state`, `code` from the server action. `create()`
forces `usage='ir_cron'` and `default_get` defaults `state` to `code` (the only supported state).

| Field | Type / default | Notes |
|---|---|---|
| `ir_actions_server_id` | M2o, required, `ondelete='restrict'` | created automatically from the delegated values |
| `cron_name` | Char, stored compute of the action name (en_US) | used for ordering and logs |
| `user_id` | M2o `res.users`, required, default `env.user` | the job runs as this user; core uses `base.user_root` |
| `active` | Boolean, default True | |
| `interval_number` | Integer, default 1, required | SQL check `interval_number > 0` (`models.Constraint`) |
| `interval_type` | `minutes`, `hours`, `days`, `weeks`, `months` (default `months`) | |
| `nextcall` | Datetime, required, default now | next planned run |
| `lastcall` | Datetime | last successful run; passed to the job as context key `lastcall` |
| `priority` | Integer, default 5 | 0 = highest priority |
| `failure_count`, `first_failure_date` | managed by the scheduler | reset on success |

`numbercall` / `doall` do not exist (removed before 19). Access: only `base.group_system` has CRUD on
`ir.cron`, `ir.cron.trigger`, `ir.cron.progress` (`odoo/addons/base/security/ir.access.csv:7-9`).
Constants in v20: `MIN_RUNS_PER_JOB = 10`, `MIN_TIME_PER_JOB = 120` (seconds, was 10 in v19),
`CONSECUTIVE_TIMEOUT_FOR_FAILURE = 3`, `MIN_FAILURE_COUNT_BEFORE_DEACTIVATION = 5`,
`MIN_DELTA_BEFORE_DEACTIVATION = timedelta(days=7)`.

## ir.cron: XML record

```xml
<!-- adapted from addons/base_geolocalize/data/ir_cron.xml and addons/auth_signup/data/ir_cron_data.xml -->
<odoo>
    <record id="ir_cron_my_model_cleanup" model="ir.cron">
        <field name="name">My Module: Clean up stale records</field>
        <field name="model_id" ref="model_my_model"/>
        <field name="state">code</field>
        <field name="code">model._cron_cleanup(batch_size=200)</field>
        <field name="user_id" ref="base.user_root"/>
        <field name="interval_number">1</field>
        <field name="interval_type">days</field>
        <field name="priority">6</field>
        <!-- optional: delay the first run -->
        <field name="nextcall" eval="(DateTime.now() + timedelta(hours=2)).strftime('%Y-%m-%d %H:%M:%S')"/>
    </record>
</odoo>
```

- `model_id` takes the `model_<model_with_underscores>` xmlid generated by `ir.model`; check it with
  `odoo_xmlid`.
- `code` is evaluated by the server action engine. Available names include `env`, `model` (empty
  recordset of `model_id`), `record`/`records` (None for crons), `time`, `datetime`, `dateutil`,
  `timezone` (now `zoneinfo.ZoneInfo`, not pytz), `float_compare`, `b64encode`, `b64decode`,
  `BinaryBytes`, `Command`, `UserError`, `log`, `_logger`, `uid`, `user`.
- Wrap the record in `<data noupdate="1">` (as `addons/crm/data/ir_cron_data.xml` does) when admins
  should be able to change interval/active without `-u` reverting it. General XML data rules:
  [data-files.md](data-files.md) and [official XML guidelines](../../odoo-guidelines/guidelines/xml.md).
- Neutralized databases deactivate every cron except `base.autovacuum_job`
  (`odoo/addons/base/data/neutralize.sql`). For periodic GC prefer `@api.autovacuum` methods (see
  [api-cache.md](../../orm/references/api-cache.md)) over a dedicated cron.

## Writing the cron method (progress API)

Long jobs must process batches and report progress with `self.env['ir.cron']._commit_progress()`;
the scheduler then re-runs the action until nothing remains (or the time budget is used).

```python
# addons/base_geolocalize/models/res_partner.py:79-86
def _cron_geolocalize(self, batch_size=20):
    domain = [('should_be_geolocalized', '=', True)]
    partners_to_geolocalize = self.search(domain, limit=batch_size)
    remaining = len(partners_to_geolocalize) if len(partners_to_geolocalize) < batch_size else self.search_count(domain)
    self.env['ir.cron']._commit_progress(remaining=remaining)
    for partner in partners_to_geolocalize:
        partner.geo_localize()
        self.env['ir.cron']._commit_progress(1)
```

`_commit_progress(processed=0, *, remaining=None, deactivate=False) -> float`
- adds `processed` to the done count; `remaining` sets the remaining count (otherwise it is decreased
  by `processed`); `deactivate=True` archives the cron after this run;
- **commits** the transaction and returns the seconds left in the time budget (`0` when exhausted,
  `inf` when not called from a cron, where it just commits). Stop when it returns a falsy value:

```python
# addons/auth_signup/models/res_users.py:286-291
for user, invited_users in invited_by_users.items():
    ...
    if not self.env['ir.cron']._commit_progress(len(invited_users)):
        _logger.info("send_unregistered_user_reminder: timeout reached, stopping")
        break
```

- `_rollback_progress()` (new in 20) rolls back with the same cron semantics.
- `_notify_progress(done=, remaining=)` is deprecated since 19 (`@deprecated`): use `_commit_progress`.
- The job context holds `lastcall`, `cron_id`, `cron_end_time` and `ir_cron_progress_id`.
- Outside crons do not commit yourself (see the
  [official ORM rules](../../odoo-guidelines/guidelines/orm.md#transactions-and-exceptions));
  `_commit_progress` is the sanctioned commit point inside a cron. Python-side cron recipe:
  [recipes.md](../../orm/references/recipes.md).

## Triggering a cron from code: `_trigger`

```python
def _trigger(self, at: datetime | Iterable[datetime] | None = None, *, coalesce: int = 0)
```

- No `at`: run at the next scheduler wake-up. `at` may be one datetime or an iterable (minute
  precision). Returns the created `ir.cron.trigger` records. Override `_trigger_list(at_list)`, not
  `_trigger`.
- `coalesce` (new in 20) is a window in minutes: every trigger is shifted to the end of its window,
  limiting wake-ups for non-urgent work: `cron._trigger(coalesce=15)`.
- On an inactive cron, triggers in the past are dropped. It works without `sudo()` (triggers are
  created in sudo):

```python
# addons/base_geolocalize/models/res_partner.py:69-77
if (geo_localize_cron := self.env.ref('base_geolocalize.ir_cron_geolocalize_required_partners', raise_if_not_found=False)):
    geo_localize_cron._trigger()
```

- `ir.cron.toggle(model, domain)` activates the cron if `search_count(domain)` is non-zero (used by
  `addons/mail/models/fetchmail.py:363`), and does nothing on a neutralized database.

Source: odoo/addons/base/models/ir_cron.py:737-818, odoo/addons/base/tests/test_ir_cron.py:740-790

## How the scheduler runs a job

| Step | Behaviour (v20) |
|---|---|
| Acquire | job row locked; past triggers for it are deleted |
| Loop | server action called repeatedly while `loop_count < 10` **or** less than 120 s elapsed, until a status is reached; each job runs in its own `contextvars` context |
| `fully done` | action returned and `remaining == 0` (or no progress API used): rescheduled at `nextcall + interval` (interval added in the user's timezone, so the hour stays stable across DST) |
| `partially done` | remaining > 0 after the loop, or crashed after committing progress: re-queued ASAP via a trigger |
| `failed` | exception without progress, or 3 consecutive timeouts: `failure_count += 1` |
| Deactivation | after 5 failures **and** 7 days since the first failure; new in 20: an early warning is sent through `_notify_admin` (mail override) before that |

`method_direct_trigger()` ("Run Manually") runs the job in the current thread, needs write access on
`ir.cron`, and returns a `display_exception` client action on failure.

## ir.sequence

| Field | Notes |
|---|---|
| `name` (required), `code` | `code` is the lookup key for `next_by_code` |
| `implementation` | `standard` (PostgreSQL sequence `ir_sequence_%03d`, fast, gaps on rollback) or `no_gap` (row lock, slower) |
| `prefix`, `suffix` | `%(key)s` interpolation, `trim=False` |
| `number_next`, `number_next_actual`, `number_increment`, `padding` | `padding` left-pads with zeros |
| `company_id` | default `env.company`; set `eval="False"` for a shared sequence |
| `use_date_range`, `date_range_ids` | per-period sub-sequences (`ir.sequence.date_range`: `date_from`, `date_to`, `number_next`), auto-created per calendar year |

Interpolation keys: `year month day y doy woy weekday h24 h12 min sec isoyear isoy isoweek`, each also
as `range_<key>` (start of the date range) and `current_<key>` (now). Dates use the user timezone
(`env.tz`). New in 20: an onchange warns about non-ASCII prefix/suffix (Code128 barcodes).

```xml
<!-- addons/sale/data/ir_sequence_data.xml (whole file is noupdate="1") -->
<record id="seq_sale_order" model="ir.sequence">
    <field name="name">Sales Order</field>
    <field name="code">sale.order</field>
    <field name="prefix">S</field>
    <field name="padding">5</field>
    <field name="company_id" eval="False"/>
</record>
<!-- prefix with the year: addons/stock_landed_costs/data/stock_landed_cost_data.xml -->
<field name="prefix">LC/%(year)s/</field>
```

```python
# addons/sale/models/sale_order.py:1452-1467
@api.model_create_multi
def create(self, vals_list):
    for vals in vals_list:
        if vals.get("name", self.env._("New")) == self.env._("New"):
            seq_date = (
                fields.Datetime.context_timestamp(self, fields.Datetime.to_datetime(vals["date_order"]))
                if "date_order" in vals else None
            )
            vals["name"] = self.env["ir.sequence"].with_company(
                vals.get("company_id")
            ).next_by_code("sale.order", sequence_date=seq_date) or self.env._("New")
    return super().create(vals_list)
```

- `next_by_code(sequence_code, sequence_date=None)` (`@api.model`) picks the sequence of
  `env.company` or with no company (ordered by `company_id`), returns `False` if none: always keep a
  fallback. `next_by_id(sequence_date=None)` on a sequence record.
- Both call `check_access('read')`: `base.group_user` has read, portal/public code needs `sudo()`.
- Use `with_company(...)` to number per company; `sequence_date` selects the date range.

## ir.actions.server

`state` values (selection; mail and sms add some):

| state | Module | Runs | Key fields |
|---|---|---|---|
| `object_write` | base | update a field (path) | `update_path`, `evaluation_type` (`value`/`sequence`/`equation`), `value`, `resource_ref`, `selection_value`, `update_boolean_value`, `html_value`, `update_m2m_operation` |
| `object_create` | base | create a record | `crud_model_id`, `value`, `link_field_id` |
| `object_copy` | base | duplicate a record | `crud_model_id`, `resource_ref` |
| `code` | base | Python in `code` (`groups='base.group_system'`) | return an action by assigning `action = ...` |
| `webhook` | base | POST to `webhook_url` | `webhook_field_ids` |
| `multi` | base | run `child_ids` in sequence | `child_ids` |
| `next_activity` | mail | schedule an activity or an activity plan | `activity_type_id` or `activity_plan_id` (not both), `activity_summary`, `activity_note`, `activity_date_deadline_range(_type)`, `activity_user_type` (`specific`/`role`/`generic`) |
| `mail_post` | mail | post `template_id` (message_type `auto_comment`, subtype `mail.mt_comment`) on mail.thread models, otherwise `send_mail_batch` | `template_id`, `mail_post_autofollow` |
| `log_note` | mail (new in 20) | log `log_note_note` (Html, translatable) as a note | `log_note_note` |
| `followers` / `remove_followers` | mail | (un)subscribe partners | `followers_type`, `partner_ids`, `followers_partner_field_name`, `subtype_ids` |
| `sms` | sms | send `sms_template_id` | `sms_template_id` |

Bound to the Action menu ("gear") of a model, from XML:

```xml
<!-- addons/project/views/project_project_views.xml:924-934 -->
<record id="action_server_convert_project_to_template" model="ir.actions.server">
    <field name="name">Convert to Template</field>
    <field name="model_id" ref="project.model_project_project"/>
    <field name="binding_model_id" ref="project.model_project_project"/>
```

- `binding_view_types` default `list,form`; `binding_type` `action` (default) or `report`.
- Execution check (`_can_execute_action_on_records`): if `group_ids` is set the user must be in one
  of them; otherwise the user needs `write` access on the model. `state` has no default: always set it.
- `explanation` (Text, new in 20 on every `ir.actions.*`): verbose description of what the action
  does, exposed by `api_doc` and written for AI agents (`addons/crm/views/crm_lead_views.xml:1020`).
- Override runners per state: `_run_action_<state>` or `_run_action_<state>_multi(eval_context=None)`.
- Python helpers: `create_action()` / `unlink_action()` set or clear `binding_model_id`.

## v19 habit -> Odoo 20

| v19 / older | Odoo 20 | Source |
|---|---|---|
| Expect ~10 s per cron batch loop | budget `MIN_TIME_PER_JOB = 120` s (and at least 10 runs) | odoo/addons/base/models/ir_cron.py:36 |
| `cron._trigger(at)` only | `cron._trigger(at, coalesce=minutes)` | odoo/addons/base/models/ir_cron.py:750 |
| `self.env.cr.rollback()` in a cron | `self.env['ir.cron']._rollback_progress()` | odoo/addons/base/models/ir_cron.py:918 |
| `_notify_progress(done=, remaining=)` | `_commit_progress(processed, remaining=)` | odoo/addons/base/models/ir_cron.py:849-916 |
| `get_param('database.is_neutralized')` | `get_bool(...)` (flagged by odoo_validate rule ORM001) | odoo/addons/base/models/ir_cron.py:740 |
| `pytz.timezone` in server action code | `timezone` is `ZoneInfo` (no `.localize()`; ORM015) | odoo/addons/base/models/ir_actions.py:133 |
| `mail_post_method` = email/comment/note | `state='mail_post'` or `state='log_note'` + `log_note_note` (ORM024) | addons/mail/models/ir_actions_server.py:23-37 |
| `activity_type_id` only for `next_activity` | also `activity_plan_id`, `activity_user_type='role'` + `activity_role_id` | addons/mail/models/ir_actions_server.py:84-125 |
| `numbercall`, `doall` on crons | removed (use `active`, `_commit_progress(deactivate=True)`) | odoo/addons/base/models/ir_cron.py:108-124 |
